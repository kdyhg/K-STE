# 사용 예시

## 1. 요구사항과 제약만 변경

### 입력

```text
작업 요구사항 및 제약 조건에만 K-STE를 적용해줘.

## 작업 요구사항
게시글에서 첨부파일을 좀 위로 올리고, 링크도 적당히 추가해줘.

## 제약 조건
기존 것들은 손대지 마.

## 설명
기존 디자인이 마음에 들어.
```

### 출력 예시

```text
## 작업 요구사항
1. 게시글의 첨부파일 영역을 슬라이드 영역보다 위에 배치한다.
2. 게시글에 링크를 첨부하는 기능을 추가한다.
3. [확인 필요: 링크의 표시 방식과 열리는 위치]

## 제약 조건
[확인 필요: 변경하지 않아야 할 기존 기능 또는 데이터의 범위]

## 설명
기존 디자인이 마음에 들어.
```

**설명** 영역은 바꾸지 않는다. 원문에 없는 디자인 규격이나 링크 개수를 만들지 않는다.

## 2. 점검만 실행

```text
이 프롬프트의 결과물 형식만 K-STE로 점검해줘. 고치지는 마.
```

응답은 문제 위치와 이유만 제시한다.

## 3. 허용 영역 밖 수정 금지

```text
K-STE를 제약 조건에만 적용해줘.
UI 설계에는 어떤 지침도 추가하지 마.
```

`제약 조건` 이외의 설명과 요구사항은 유지한다.

## 4. 요청이 불명확할 때

```text
K-STE로 전부 알아서 최적화해줘.
```

`전부`은 명시적 전체 적용 요청일 수 있으나 무엇을 보존할지 판단해야 한다. 원문을 확인하고 의미 보존 범위 안에서만 수정한다.

## 5. 개발 작업과 함께 사용

```text
아래 기능을 구현해줘. 단, DB 제약 조건을 실행 전에 K-STE 원칙으로 점검해.
```

명확화는 DB 제약 조건에 국한한다. 사용자가 실행을 요청한 개발 작업을 단순한 프롬프트 재작성 요청으로 바꾸지 않는다.

## 6. 기술 설명에만 출력 명확화 적용

```text
이번 답변의 기술 설명 부분만 K-STE로 작성해 줘.
개념의 정의와 적용 조건은 정확하게 보존해 줘.
```

예를 들어 비동기 처리 방식을 설명할 때, 정의와 예시를 구분하고 주어나 대상을 분명하게 쓴다. 일상적인 인사말까지 변형하지 않는다.

## 7. 학습 설명에만 적용

```text
미분계수와 도함수의 관계를 설명해 줘.
학습 설명에만 K-STE를 적용하고, 전제·논리·수식은 생략하지 마.
```

설명을 짧게 하려고 수학적 조건이나 증명 단계를 누락하지 않는다.

## 8. 오류 설명에만 적용

```text
이 오류의 원인을 설명할 때 K-STE를 적용해 줘.
확인된 증상과 원인 가설, 확인 방법, 해결책을 구분해 줘.
```

확인되지 않은 원인을 사실처럼 단정하지 않는다.

## 9. 양방향으로 부분 적용

```text
프롬프트의 제약 조건만 K-STE로 정리해 줘.
그 뒤 오류 설명 부분에만 K-STE를 적용해서 답변해 줘.
다른 부분은 자유롭게 작성해 줘.
```

검사기 예시:

```bash
python scripts/kste_lint.py conversation.md --direction both --scope input:constraints,output:error
```

사용자가 양방향을 요청해도 전체 지시문과 전체 답변을 강제로 수정하지 않는다.
